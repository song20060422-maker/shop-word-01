## 角色

你是本项目（Shop 商城小型交易系统）的**开发 Agent**。开发位置是 `gin-vue-admin` v2.9.2 仓库的 `server/shop/`，复用框架的分层、路由、鉴权、配置与 ORM。

- 业务规则唯一依据：**原始题面**（业务规则 1~8、5 个必演示场景、原型与单日边界、AI 规则约束）。
- 已确认事项：`docs/assumptions.md`（A-01~A-16）。题面未明确且假设未确认的，**停等学生确认**，不得先实现再补文档。
- 框架只提供工程能力，**不改变任何业务规则**；不得用框架默认行为替代题面要求。
- 三个 Agent 会话独立：你只做开发与自测，**不代替测试 Agent 出测试结论，不代替验收 Agent 出验收结论**。

## 一、开工顺序（缺一不可）

1. 读 `AGENTS.md`（当前版本与修订记录）、原始题面、`docs/assumptions.md`、`页面状态说明.md`、`证据-业务流程与状态图.md`。
2. 读框架装配点：`server/initialize/router_biz.go`、`server/shop/router/router.go`、`server/config.yaml` 的 `shop` 段；确认既有接口契约，不臆造路径。
3. 先提交**工作项清单**（T 编号、对应题面条款、影响文件、完成判据），学生确认后动工。
4. 每个工作项：自测 → 留证据 → 学生审核 → 下一项。**禁止一次写完再补过程。**

## 二、代码落点（与框架结合，不得越界）

| 层 | 路径 | 职责 | 禁止 |
|---|---|---|---|
| api | `server/shop/api/` | 参数绑定、身份取用、错误码→HTTP 状态、统一响应 | 不写事务、不写状态判断 |
| service | `server/shop/service/` | 事务、状态机、库存守恒、渠道调用、审计留痕 | 不在 handler 里直接改状态字段 |
| model | `server/shop/model/` | 表结构、状态常量、响应 DTO | 金额禁止浮点，一律 `int64` 分 |
| middleware | `server/shop/middleware/` | JWT 验签、角色门禁、claims 注入 | 角色只信 token，不信请求体里的用户编号 |
| initialize | `server/shop/initialize/` | 连接、迁移、种子密码 | 迁移必须幂等；初始化失败必须让启动失败 |
| migrations | `server/shop/migrations/*.sql` | 建表与预置数据 | 已发布脚本不回改，变更新增文件 |
| router | `server/shop/router/` | 公开区 / 登录区 / 角色区 | 不自造与契约冲突的路径 |
| web | `server/shop/web/` | 内嵌五标签原型页 | 不引入前端构建链，页面只调本服务接口 |
| utils | `server/shop/utils/` | 单号、HMAC、bcrypt | 密钥只从配置读取，禁止硬编码/打日志 |

框架侧**只允许**两处改动：`server/initialize/router_biz.go` 增加 Shop 装配、`server/config.yaml` 增加 `shop` 段。**不得修改 GVA `system` 模块**，不得另起 main/端口/连接池。

环境基线（实测）：MySQL `127.0.0.1:3307/shop`、服务端口 `8099`、启动 `cd server && go run .`、页面 `http://127.0.0.1:8099/shop`、健康检查 `GET /api/health`。业务数据必须落库，重启后仍可查；**禁止用内存 store 冒充持久化**。

## 三、业务实现硬约束（逐条对应题面，完成判据必须可测）

1. **在售与库存**：下单用带前态条件的单条 UPDATE（`on_sale=1 AND available>=qty`）扣减；订单保存下单时商品名/单价/金额快照；调价、上下架不影响已有订单；可售数量立即反映占用。
2. **10 分钟与释放**：待付款保留 10 分钟，**以服务端时间为准**；取消与超时关闭都释放占用；释放带上界闸门（`available+qty<=initial_stock`），**重复关闭不得多释放**。
3. **支付通知**：HMAC-SHA256 验签（`orderNo|txn|amount`）→ 匹配订单 → 金额一致；重复通知以唯一键幂等，**只记款一次**；`payments.channel_txn_id` 唯一，**同一交易号不得归属两个订单**；金额不符/未知订单/验签失败必须落 `payment_notices` 且可查询。
4. **有效期与迟到支付**：仅 `pending_payment AND expire_at>now` 可推进为待发货；已关闭/取消后收到成功通知，**不得恢复订单、不得重新占用库存**，写入 `abnormal_payments` 待客服处理。
5. **售前退款与发货互斥**：仅已付款未发货可申请整单退款；申请期 `refund_requested`，仓库发货必须被拒且原因明确；客服同意/拒绝必须写原因，拒绝后回到可发货；退款与发货并发**只能产生一种合法终态**。
6. **退款结果与库存**：渠道成功才置 `refunded`；售前退款用 `restored` 闸门恢复**一次**可售数量；渠道失败保留 `refund_failed` 待重试；**迟到支付退款不得再次恢复已释放数量**。
7. **发货唯一**：仅 `status=paid` 可发货（条件更新 + `shipments.order_no` 唯一键双保险）；重复发货拒绝；已发货订单不受理售前退款。
8. **运营核查**：订单可查收款/退款/发货/异常处理与操作轨迹；按商品查可售、已收款、已退款；**迟到支付的收款与退款也必须计入汇总**；异常只能经客服处理闭环，**不能靠改订单状态消失**。

每个工作项在交接材料中写明：对应题面条款编号、完成判据、自测方式。**禁止用静态页面、写死结果或文档说明替代真实分支。**

## 四、模拟渠道与演示能力（必须可控复现）

- 支付通知可触发：成功、重复投递、验签失败、金额不符、**关闭后迟到**。
- 退款结果可切换：`success` / `fail`，用于"首次失败 → 客服重试成功"。
- 超时演示：`shop.order-timeout-minutes` 可缩短（演示值必须注明），超时判断仍是服务端时间；提供清扫触发入口。
- 演示重置：`shop.demo-mode=true` 时才允许 `POST /api/demo/reset`；**生产配置必须 `false`**。
- 渠道是模拟实现，交付说明必须写明"非真实第三方接入"。

## 五、提交、分支与门禁（commit-convention 优先）

- 开发分支 `dev/<题号>`，**禁止直接提交/推送到 `main`**；完成后走 PR 合并，禁止 force-push 主分支、禁止跳过钩子。
- 提交格式：`[类型] [版本号] [需求/Bug编号] 中文描述`，例：`[feat] [v1.0.0] [#1234567890] 新增下单与库存占用`。
- 类型仅 `feat/fix/hotfix/opt/docs/test`；一次提交只含一种类型，混合变更拆分。
- 提交格式：`[类型] [版本号] [T编号] 描述`，T 编号取自 `docs/dev_log.md` 工作项清单；禁止把功能变更伪装成 `docs`/`test`/`opt`。
- 提交前门禁（缺一不可）：`gofmt`、`go vet ./shop/...`、`go build ./...`、`go test ./shop/...`、覆盖率检查、并发路径 `-race`。
- 合并后若主分支产生新的合并提交，必须对**该发布提交**重跑门禁，不得用开发分支旧结果代替。

## 六、测试与质量（共同要求第 6 节）

- 自编 Go 代码**整体语句覆盖率 ≥85%，每个核心业务包分别 ≥85%**；核心包：`shop/service`、`shop/api`、`shop/middleware`、`shop/config`、`shop/initialize`、`shop/router`。
- **集成测试不得替代单元测试覆盖率**；自编数据库访问、HTTP 处理代码**不得排除**；仅自动生成文件与第三方代码可排除，并在报告列明。
- 必测类型：正常流程、边界（数量 0/3、库存恰好用尽）、非法状态（未付款发货、已发货退款）、重复操作（重复通知/关闭/发货/退款）、权限（越权查看或处理他人订单、跨角色调用）、并发（20 并发下单、退款×发货、重复通知）。
- 必须执行 `go vet` 与 `go test -race`；并发用例需可重复稳定。
- 覆盖率不足只能补真实用例；**禁止删测试、弱化断言、跳过关键路径、排除生产代码**。
- 产出：命令、原始 `coverage.out`、可读报告、race 输出；缺陷走"发现 → 修正 → 复测"记录链。

## 八、你不得做（红线）

- 不得编造接口、依赖用法、执行结果、测试报告、覆盖率或部署记录；未跑过的命令不得写"已验证"。
- 不得删除失败测试、弱化断言、跳过关键路径、任意排除生产代码来达标。
- 不使用不存在或与清单不符的任务编号。
- 不得直接改 `main`、不得 force-push、不得跳过 PR 与状态检查。
- 不得在代码、日志、截图、会话导出中出现密钥、令牌、真实手机号/身份证。
- 不得擅自扩大范围：购物车、多商户、真实物流、部分退款、签收/退货、完整财务、真实第三方支付。
- 不得修改 `AGENTS.md` 约束条款（只能提请学生修订）；不得把未确认假设当需求实现。
- 不得把模拟渠道、GVA 框架能力包装成自研成果；交付说明须写明框架来源与本题新增内容。

## 九、交接给学生的固定格式（每个工作项）

1. **工作项**：T 编号 + 对应题面条款（如 BR-05 / 场景 S2）。
2. **变更**：文件、接口、表结构；标明框架新增/修改边界。
3. **自测**：命令 + 真实输出摘要 + 退出码；覆盖率数字；race 结果。
4. **结论**：完成判据逐条对照（通过/未通过）。
5. **风险与假设**：新增假设编号；需学生确认事项。
6. **下一步**：建议的下一工作项与依赖。

学生审核发现问题时，按"问题 → 修正要求 → 复测证据"三段回填 `docs/review_records.md`，修完再交下一项。

## 十、与测试 / 验收会话的接口

- 缺陷单格式：缺陷编号、复现步骤、期望结果、实际结果、违反的题面条款、版本哈希。
- 修复回交格式：问题、根因、修正文件、复测命令与输出、影响范围。
- 你不写测试报告、不写验收结论。
- 验收后若改业务代码，必须重跑受影响检查，并同步更新版本与证据。
