# Agent 验收（独立验收 Agent 会话任务书）

> 适用题目：小型商城交易系统（下单 / 支付 / 发货 / 售前退款 / 异常处理）
> 验收依据：原始题面全文（含"业务背景与现场情境""参与角色与业务起点""需要完成的业务范围与规则 1–8""必须演示的完整工作场景""原型、Skill 与单日边界""AI 规则约束"），不含学生自写文档对题意的改写。
> 验收人：独立验收 Agent（与开发 Agent、测试 Agent 分属不同会话，上下文互不可见）。

---

## 1. 验收会话要求

### 1.1 会话独立性
- 验收 Agent 在**全新独立会话**中启动，不加载开发/测试会话的对话历史、工作笔记或测试结论。
- 验收输入只允许：① 原始题面；② 最终版本源码与运行材料；③ 学生按交接清单提供的材料（部署地址、数据库初始化脚本、账号口令、Skill 文件、AGENTS.md 历史版本、证据目录）。
- 开发 Agent 与验收 Agent 不得互相改写对方的输出；验收结论只出自验收会话。

### 1.2 验收环境与副作用边界
- 验收在**隔离副本**上执行：独立数据库/独立 Redis key 前缀/独立端口，不触碰真实凭证与真实数据。
- 验收 Agent 为只读+隔离执行：不改生产代码、不补写测试、不修改提交历史、不触发部署。
- 执行任何脚本前先审阅命令副作用；不具备安全执行条件的检查项记录"无法执行及原因"，不得记为通过。

### 1.3 验收输入材料清单（缺失即登记"待补证"）
| 编号 | 材料 | 用途 |
|---|---|---|
| M1 | 最终版本 commit 哈希 + 构建制品版本 | 版本对应关系 |
| M2 | 数据库/缓存初始化脚本与预置数据说明 | 环境搭建（2 商品、3 买家、员工账号、单价 10000 分、可售 5 件） |
| M3 | 各角色账号：买家×3、运营、仓库、客服 | 场景执行 |
| M4 | 启动方式（本地命令或部署地址） | 启动验证 |
| M5 | 单元测试及覆盖率原始 profile | 覆盖率核验（整体及核心包 ≥85%） |
| M6 | AGENTS.md 全部历史版本 + 加载记录 | AI 约束核验 |
| M7 | 业务 Skill + 验收 Skill 文件与调用记录 | Skill 核验 |
| M8 | 证据目录（截图/日志/接口响应，已脱敏） | 证据引用 |

## 2. 验收项矩阵（依据原始题面逐项拆解）

每项记录：`编号、题面来源、验收方法、通过标准、结论、证据位置`。结论取值：通过 / 部分通过 / 失败 / 待补证 / 不适用（须写明条件）。

### 2.1 业务规则验收项（R1–R8）

| 编号 | 题面要求 | 验收方法 | 通过标准 |
|---|---|---|---|
| R1 | 只能购买在售且数量足够的商品；订单保存下单时商品与价格；上下架/调价不影响已有订单；可售数量反映已占用 | 下单前调价、下架再查旧订单；下单后核对库存占用 | 旧订单金额不变；可售数=库存-已占用（含待付款占用）；越界下单被拒 |
| R2 | 待付款保留 10 分钟；主动取消/超时关闭释放占用；重复关闭不多释放；服务端时间判断 | 创建订单→改服务端时间或等定时任务→关闭两次；再查可售数量 | 超时以服务端时间为准；两次关闭后可售数量只恢复一次的量 |
| R3 | 支付通知须鉴权、匹配订单及金额；重复通知不重复记款；渠道交易号不归属两个订单；金额不符/未知订单/验签失败可查询处理结果 | ① 同一成功通知重发 2 次 ② 用同一渠道交易号构造指向另一订单的通知 ③ 改金额 ④ 错签名 ⑤ 未知订单号；逐个查处理结果 | 记款幂等；交易号绑定校验拒绝；三类异常均有可查询的处理记录与原因 |
| R4 | 有效期内校验通过的通知→待发货；超时关闭后收到成功通知→不恢复订单、不重新占用库存，进入异常支付待处理列表，由客服核实后发起退款 | 订单创建后关闭，再发送合法成功通知；查订单状态、可售数量、异常支付列表 | 订单保持已关闭；可售数量不变；通知进入异常列表；客服可发起退款 |
| R5 | 已付款未发货可申请整单退款；申请期间暂停发货；客服同意/拒绝并写原因；拒绝后可继续发货；退款与发货并发只形成一种合法结果 | ① 申请退款后仓库尝试发货 ② 客服拒绝后仓库发货 ③ 发货与退款审批并发触发 | 申请期发货被拒；拒绝原因落库；并发后订单终态唯一且合法（已发货 或 已退款），不出现"已发货且已退款" |
| R6 | 退款经模拟渠道确认成功后买家可见退款结果；正常售前退款恢复可售数量；渠道明确失败保留待处理记录由客服重试；迟到支付退款不得重复恢复已释放数量 | ① 退款首次模拟失败→客服重试→成功 ② 迟到支付订单退款后核对可售数量与退款流水 | 失败保留待处理记录；重试成功后状态与数量一致；迟到支付退款后可售数量不二次增加、退款流水不重复 |
| R7 | 仓库只能为合法待发货订单登记一次发货；已发货不受理本题售前退款 | 同一订单调用发货登记 2 次；已发货订单申请退款 | 第二次发货被拒；已发货订单退款申请被拒且有明确原因 |
| R8 | 运营按订单查收款/退款/发货/异常处理记录；查可售数量、已收款、已退款汇总；异常记录不能靠直接改订单状态消失 | 各场景后查运营汇总页；尝试直接改库/调接口篡改异常记录 | 四类记录完整可追溯；汇总数=流水聚合；异常记录仅能通过客服处理流程闭环，直改无效或被拒绝 |

### 2.2 完整工作场景验收项（S1–S5，每项按"起点→多角色操作→正常/异常分支→持久化结果→最终核查"执行）

| 编号 | 场景 | 关键验证点 |
|---|---|---|
| S1 | 正常成交：运营上架→买家购买付款→仓库发货→买家查运单→运营核查收款与库存 | 买家端可见运单号；运营端收款与库存数字与流水一致 |
| S2 | 缺货与弃单：20 个并发下单争抢 5 件（每单 1–2 件）→部分订单未付款关闭→其他买家购买释放的商品 | 并发结果成功单总量≤5 件且无超卖；关闭后释放量正确；后续买家能买到释放数量 |
| S3 | 售前退款：付款→申请→仓库尝试发货受限→客服批准→首次退款失败、再次成功→订单与数量恢复一致 | 发货受限有记录；失败后待处理记录存在；成功后订单、退款、可售数量三方一致 |
| S4 | 迟到支付：订单先关闭→成功通知到达→客服从异常列表发现→发起退款→运营确认无重复释放和重复退款 | 见 R4/R6；运营汇总中该笔"已收款"与"已退款"成对出现且各一次 |
| S5 | 操作竞争：退款申请与发货并发、重复支付与退款通知、越权查看/处理他人订单 | 每类并发/越权操作均有明确结果（拒绝或唯一合法终态），无脏数据 |

### 2.3 原型与边界验收项（P1–P4）

| 编号 | 题面要求 | 通过标准 |
|---|---|---|
| P1 | 原型覆盖：商品与订单页、仓库待发货页、客服退款及异常支付页、运营核查页（可合并标签页） | 逐一走查，缺页即失败 |
| P2 | 预置数据：2 个商品、3 个买家、员工账号；一种商品单价 10000 分、可售 5 件 | 初始化后实际查询核对 |
| P3 | 每单仅一种商品、数量 1–2 件、人民币分、无运费优惠 | 边界值 0/3 被拒；金额单位为分 |
| P4 | 不做购物车、多商户、真实物流、部分退款、签收退货 | 超范围功能不存在（存在未接通或半成品同样扣分） |

### 2.4 AI 规则约束验收项（C1–C11）

| 编号 | 题面要求 | 验收方法 |

| C5 | 业务规则以题面为准；未明确事项记录假设 | 查假设记录文档，且假设未与题面冲突 |

| C7 | 禁止编造接口、依赖用法、执行结果、测试报告、部署记录 | 抽查关键接口真实存在且可调；复跑报告对应测试 |
| C8 | 禁止删失败测试、弱化断言、跳过关键路径、任意排除生产代码达标 | 对比测试历史 diff；检查覆盖率排除清单 |
| C9 | 禁止泄露密钥与敏感信息；日志、截图、对话导出脱敏 | 扫描证据目录与日志中的口令/密钥 |
| C10 | AI 生成代码经学生检查，错误保留问题、修正要求与复测过程 | 查修订记录链 |
| C11 | 提交约束文件历史版本、实际加载记录及对应任务；说明约束了哪些行为、是否调整及原因 | 逐版本核对，缺失即失败 |

## 3. 证据位置约定

验收产生的证据统一存入 `evidence/` 目录，命名 `{验收项编号}_{序号}_{内容}`，所有截图/日志/响应先脱敏后入库：

```text
evidence/
├── R1_01_旧订单金额不变_接口响应.json
├── R2_01_重复关闭库存恢复一次_库存快照.png
├── R3_01_重复通知幂等_响应日志.txt
├── ...
├── S2_01_20并发下单_压测输出.txt
├── S2_02_并发后库存核对_查询响应.json
├── C1_01_AGENTS.md_v1_git_show.txt
├── ...
└── summary/验收汇总表.csv
```

规则：每条结论至少 1 条证据；证据必须可复现（附命令与时间）；无法脱敏的原始数据不作为证据提交。

## 5. 验收执行流程与退出条件

1. **会话开启**：新会话加载本任务书 + 原始题面 + 交接材料 M1–M8；确认隔离环境就绪。
2. **版本锁定**：记录 commit 哈希、构建版本、数据库初始化结果（截图入 `evidence/`）。
3. **按序执行**：R1–R8 → S1–S5 → P1–P4 → C1–C11 → K1–K2；单项失败定位到具体步骤并继续其余项，不因单项失败中断全量验收。
4. **回填记录表**：逐项写结论 + 证据位置；"不适用"必须写明条件与理由，缺失证据一律"待补证"。
5. **汇总判定**：统计通过/部分通过/失败/待补证比例；列出必做项未通过清单（题面规则 1–8 与场景 S1–S5 均为必做，任何一项未完全通过即验收不合格）。
6. **产出**：① 本验收会话的完整对话记录（含所有提示词与工具结果）；② 回填后的逐项结论记录表；③ `evidence/` 证据目录及索引。三项齐备方可宣告验收完成。
7. **禁止事项**：不得为通过验收修改生产代码或测试（发现问题回给开发 Agent 处理后重新验收）；不得用文档声明替代实际执行结果；不得在验收报告中出现未脱敏信息。
